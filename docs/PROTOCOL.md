# Protocol and arithmetic design

## Client and shuffle

Each client flattens its gradient, clips it to L2 norm `C`, adds independent
Gaussian noise with standard deviation `sigma*C`, maps nonnegative values to 1
and negative values to 0, then creates `b0 <- random` and `b1 = b XOR b0`.
Packed deterministic messages deliver the shares separately.

Algorithm 2 uses independent row permutations `pi0`, `pi1` and masks. Online,
S1 sends `z1=b1 XOR a1`; S0 returns
`z0=pi0(z1 XOR b0) XOR a0`; outputs are `s0=c0` and
`s1=pi1(z0) XOR delta`. The offline correlation is
`delta=pi1(pi0(a1) XOR a0) XOR c0`, hence reconstruction is
`pi1(pi0(b))`. Chunking splits columns and never breaks client rows.

The simulator treats correlation generation as an explicit ideal offline
functionality that receives no client secret and returns only the prescribed
local views. This is a setup assumption, not a third online party or fallback.

## ADR-001: arithmetic ring and comparison

Accepted decision: arithmetic sharing uses `Z/(2^64)`. Values serialize as
little-endian `uint64`; signed integers use two's-complement and decode to the
range `[-2^63,2^63-1]`. This matches efficient local wrapping arithmetic and a
bitwise GMW comparison.

For N clients, dimension d and threshold T, Hamming counts lie in `[0,d]`,
weights in `[0,T]`, and a coordinate accumulator in `[-N*T,N*T]`.
`validate_aggregation_bounds` rejects configurations for which these values
reach the signed 64-bit boundary. Thus modular wrapping cannot alter a valid
comparison or final sign.

B2A uses one-time correlated Boolean/arithmetic bits (daBits): parties open
only `b XOR r`, never `b`. Multiplication uses one-time Beaver triples and opens
only `x-a` and `y-b`; consumed triple identifiers cannot be reused. A2B
bit-decomposes each party's own arithmetic share, XOR-shares those bits, and
adds the two bounded-width values with GMW ripple-carry gates. Public-threshold compare
and final sign extraction then operate on shared bits. Preprocessed daBits and
triples are generated by the same ideal-correlation setup assumption.

## Algorithm 3

For public reference r, the parties compute shared mismatch bits, B2A Hamming
counts, `m_i=[hd_i<T]`, `w_i=(T-hd_i)m_i`, signed values `2s-1`, Beaver-weighted
sums, and a shared nonnegative test. Hamming counts, masks, weights, and client
contributions remain in party registries. The public output object contains only
final direction shares, public T, aggregate metrics, and timing.

Normalization by `sum_i w_i` is omitted: whenever that denominator is positive
it is common and positive, so it cannot change a coordinate sign. If all
weights are zero, the unnormalized sum is zero and the documented tie rule is
`+1`. Oracle tests cover accepted, rejected, tie, malicious-bit, and chunk cases.
For scalability, A2B/comparison circuits use the smallest public bit width that
is sufficient for the proven value bound: `bit_length(d)` for Hamming counts
and `bit_length(N*T)+1` for signed weighted accumulators. Arithmetic shares stay
in `Z/(2^64)`; truncating the bit decomposition is correct because addition of
the low k bits reconstructs the secret modulo `2^k`, and the preflight bound
guarantees the true value fits that unsigned or two's-complement range.
